# apps/server — буде пізніше

Зараз сервера немає: додаток працює повністю офлайн, дані між телефонами переносяться файлом `.gen`.
Нижче — запропонована схема майбутньої автоматичної синхронізації. Телефонна частина вже підготовлена до неї.

## Що вже є в телефоні

- Кожен запис має `id` (UUID v7, генерується в телефоні), `created_at`, `updated_at`, `deleted_at`,
  `author_id`, `device_id`, `version`. Видалення лише мʼякі.
- Кожна локальна зміна в тій самій транзакції пишеться в таблицю `outbox`
  (`op`, `entity`, `entity_id`, `payload_json` — повний запис після зміни, `at`, `synced_at = NULL`).
- Zod-схеми, перевірка прав (`checkPermission`) і злиття (`planMerge`, `compareVersions`) лежать у
  `packages/shared` — сервер використовує той самий код.

## Протокол

### 1. Push: телефон → сервер
`POST /sync/push` `{ deviceId, changes: OutboxRow[] }` (порціями по ~500, у порядку `outbox.id`).

Сервер для кожної зміни:
1. Автентифікує пристрій/користувача (токен пристрою, виданий при реєстрації адміном).
2. Валідує `payload` zod-схемою з `@gen/shared`.
3. Перевіряє права `checkPermission(actor, op, entity, existing, serverNow)` — правило «оператор редагує свої записи 24 год»
   рахується за **серверним** часом, а не часом телефона.
4. Last-write-wins: застосовує, якщо `compareVersions(incoming, existing) > 0` (більший `updated_at`, далі `device_id`).
   Програшна версія фіксується в журналі конфліктів, як і при імпорті файла.
5. Присвоює запису монотонний `server_seq` (bigserial).

Відповідь: `{ accepted: id[], rejected: { id, reason }[] }`. Телефон ставить `synced_at` для прийнятих;
відхилені показує адміну.

### 2. Pull: сервер → телефон
`GET /sync/pull?cursor=<server_seq>&limit=1000` → `{ changes: Row[], nextCursor, hasMore }`.

Телефон застосовує зміни тим самим `planMerge` (без запису в outbox) і зберігає курсор у `local_meta`.
Свої ж зміни, що повернулися, — ідентичні, тому ігноруються (ідемпотентність).

### 3. Порядок циклу
push → pull (до `hasMore = false`) → перевірка цілісності (`checkIntegrity`) → попередження адміну.
Запуск: при появі мережі, вручну кнопкою, і раз на N хвилин, поки додаток відкритий.

## Схема на сервері

PostgreSQL, ті самі таблиці й поля, плюс `server_seq bigint` (індекс) і `received_at`.
Таблиці `devices` (id, назва, власник, токен-хеш, відкликано) та `sync_conflicts`.
Хеші PIN синхронізуються як є; вхід у веб-інтерфейс (якщо буде) — окремими паролями.

## Що врахувати

- Годинник телефона може бути неправильним: сервер відхиляє `updated_at` далі ніж на +1 добу від свого часу.
- Перший підʼєднаний телефон завантажує повний знімок (той самий формат, що й файл експорту).
- Обмін файлами `.gen` лишається запасним каналом і далі працює поряд із синхронізацією.
